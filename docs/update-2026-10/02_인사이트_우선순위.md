## 0. 결론 요약

1. 라이브는 9월 17일 빌드이고 공고 데이터는 9월 22일에 멈춰 있다. 10월에 합친 기능과 매일 갱신한 데이터가 사용자에게 가지 않는다. 배포 복구가 이번 릴리스의 전제이고, 토큰 등록이나 Vercel 연동은 제품 주인만 할 수 있다.
2. 지금 그대로 배포하면 10월 3일에 들어간 '예상 일정 → 실제 공고 자동 이동'이 모든 사용자 데이터에 처음 실행된다. 그룹 단위 예상(LG그룹, 카카오그룹 등)이 계열사 공고 한 곳으로 옮겨지므로 배포 전에 막아야 한다.
3. 기업 형태 정보가 없는 공고는 기업 형태 조건을 하나라도 고르면 사라진다. 10월 14일 기준 접수 중 공고 190건 중 82건(43%)이 여기에 해당하고, 원티드 공고와 제보 공고는 전부 해당한다.
4. 핵심 사용 흐름은 '접수 중 공고 찾기 → 담기 → 마감 D-day 보기 → 결과 기록'이다. 이 흐름에서 예상 날짜와 확정 날짜, 담은 것과 낸 것이 화면에서 구분되지 않고, 밀린 결과는 기본 보기(표)에 보이지 않는다.
5. 라이브에도 있는 기록 안전 문제를 Must에 넣었다. 계정 데이터를 불러오지 못하면 앱이 빈 보드로 시작하고, 처음 쓰는 사람에게 뜨는 '내 조건' 창에서 저장을 누르면 서버의 기록이 빈 값으로 덮인다(F23). 로그아웃해도 이 기기의 사본이 지워지지 않아, 같은 브라우저에서 새 계정을 만든 사람이 앞사람의 지원 기록과 자소서를 가져갈 수 있다(F21, UX 04 문서 G-17).
6. 추천 범위는 Must 10건(약 2.25일)과 Should 2건(약 0.5일)이다. 배포 차단 조건은 B01(배포 경로)과 B04(자동 이동 안전장치)다. 빈 기록 저장 제외(B09)는 저장 경로를 바꾸는 B08·B26·B28과 같은 릴리스에 겹치지 않게 다음 릴리스 첫 항목으로 미뤘다. 가상 패널 실험은 로컬 빌드에서 돌리므로 배포와 묶지 않는다. 실험 1 변형(반나절)은 릴리스 직후 만들고, 실험 2는 실험 1 결과를 본 뒤 진행한다.
7. UX 04 문서와 겹치는 항목은 5장 끝의 대응표로 맞췄다. '확인 필요' 자동 판정 기준은 서류 마감 후 14일(발표 예정일이 있으면 그 날짜)로 정했고, 화면 문구는 04 문서의 용어(담기·빼기, '형태 정보가 없는 공고')를 따른다.

**①-b 기존 테이블 집계 (테이블 추가 없음, 주인이 Supabase SQL Editor에서 읽기 쿼리 실행)**

결과 수치는 공개 문서에 싣지 않는다.

```sql
-- 최근 7일 안에 저장한 계정 수
select count(*) from jobboard_data where updated_at > now() - interval '7 days';

-- 계정별 담은 공고 수와, 그중 서류 결과가 '대기'인 수
select user_id,
       count(*) filter (where (a.value->>'applied')::boolean) as applied,
       count(*) filter (where (a.value->>'applied')::boolean and a.value->>'doc' = '대기') as waiting
from jobboard_data, jsonb_each(data->'apps') as a
group by user_id;

-- 계정별 저장 크기와 기록 수 (빈 기록 정리 전후 비교)
select user_id, pg_column_size(data) as bytes,
       (select count(*) from jsonb_object_keys(data->'apps')) as records
from jobboard_data;
```

**② DB 테이블을 추가해야 잴 수 있는 지표 (주인이 테이블 생성 SQL을 실행해야 함)**

| 지표 | 필요한 이벤트 | 쓰임 |
|---|---|---|
| 첫 화면에서 첫 행동까지 클릭 수 | open(첫 화면, 변형), view(탭 전환), 첫 기록 변경 | 실험 1을 실제 사용으로 확인 |
| 결과 기록 경로 비율 | result(어디서: 오늘·표·카드·현황표) | '오늘' 화면이 결과 기록을 앞당기는지 |
| 결과 기록까지 걸린 날 | result 시각과 마감일의 차이 | M5의 원인 분석 |
| 저장 실패율 | save_ok, save_fail | 저장 안정성 |
| 변형별 재방문 | open(변형)의 날짜 | 실험 이후 실제 사용 비교 |

```sql
-- 제안: 이벤트 기록 표 (주인이 SQL Editor에서 실행). 회사 이름·글 내용은 넣지 않는다.
create table jobboard_events (
  id bigint generated always as identity primary key,
  user_id uuid not null default auth.uid() references auth.users(id) on delete cascade,
  name text not null,                  -- open, view, apply, result, stage_date, save_fail ...
  variant text,                        -- a, b1, b2
  props jsonb not null default '{}',   -- 예: {"from":"today"}. 회사 이름·본문 금지
  created_at timestamptz not null default now()
);
alter table jobboard_events enable row level security;
create policy "insert own events" on jobboard_events for insert with check (auth.uid() = user_id);
create policy "select own events" on jobboard_events for select using (auth.uid() = user_id);
```

판단: 활성 계정이 적은 지금은 ①과 ①-b로 충분하다. ①-b의 활성 계정 수가 두 자릿수가 되면 이 표의 도입을 다시 검토한다(B22). 도입할 때는 개인정보 처리 안내에 수집 항목을 적는다.

## 4. 백로그 (RICE)

### 4.1 점수 기준

- **도달(R)**: 릴리스 뒤 2주 동안 이 변경을 겪는 활성 사용자 비율 추정(%). 사용자 수 자체를 모르므로 비율로 적는다.
- **임팩트(I)**: 3 = 핵심 흐름(찾기·담기·마감·결과)의 성공과 실패를 바꾸거나, 기록이 사라지거나 다른 사람에게 넘어간다, 2 = 핵심 흐름의 비용을 크게 줄인다, 1 = 보통, 0.5 = 작다, 0.25 = 아주 작다.
- **확신(C)**: 100% = 문제와 해결 효과가 코드·데이터·측정으로 확인됨, 80% = 문제는 확인됐고 효과는 추정, 50% = 가상 인터뷰 가설에 기댐.
- **노력(E)**: 개발자 1명 기준. XS = 1시간 안팎(0.125일), S = 2시간 안팎(0.25일), M = 반나절(0.5일), L = 하루(1일). 릴리스 전체 예산은 2~3일이다. (UX 04 문서의 난이도 S/M/L과 기준이 다르다. 이 문서의 값은 이번 릴리스 범위로 줄인 작업량이다.)
- **점수** = R × I × C ÷ E(일). 점수는 순서를 정하는 참고값이다. 하지 않으면 배포가 의미 없어지거나 데이터·보안·안내가 사실과 어긋나는 항목은 점수와 별개로 Must에 넣었다.

### 4.3 사용자 스토리와 수용 기준

**B01 배포 복구와 배포 실패 표시**
- 스토리: 취준생으로서 매일 갱신된 공고와 고쳐진 기능을 보고 싶다. 그래야 하반기 공채를 늦게 알지 않는다.
- 수용 기준
  - main 빌드가 getjob.vercel.app에 배포되고, 라이브 `data/jobs.json`의 updated가 main과 같다.
  - `VERCEL_TOKEN`이 없거나 배포가 실패하면 워크플로 실행이 실패로 표시된다. 공고 데이터 커밋은 배포와 다른 잡으로 나눠 배포 실패와 상관없이 끝난다.
  - README에 배포 절차와 이전 배포로 되돌리는 방법이 적혀 있다.
  - 주인 조치: 저장소 Secrets에 `VERCEL_TOKEN` 등록, 또는 Vercel 프로젝트의 GitHub 연동 켜기. 팀이 대신할 수 없다.

**B02 '확인 필요' 자동 판정과 표 보기 표시**
- 스토리: 결과 기록이 밀리는 지원자로서, 결과를 넣어야 할 공고를 기본 화면에서 바로 보고 싶다.
- 수용 기준
  - 서류 결과가 '대기'인데 발표 예정일이 지났거나, 발표 예정일이 없으면 서류 마감 후 14일이 지난 공고를 '확인 필요'로 자동 판정한다. 기준일은 상수 하나로 정의하고 표·카드·'오늘' 화면이 같이 쓴다(UX 04 문서 B-3-1). 카드 보기의 기존 경고(3일 기준)도 이 판정으로 바꾼다.
  - 표의 '결과 확인' 칸은 '발표 예정일'로 이름을 바꾸고 이 판정에 쓴다(UX 04 문서 M-04).
  - '확인 필요' 타일과 칩은 직접 고른 행과 자동 판정된 행을 함께 센다. QA 시드에서 표와 카드 보기의 수가 같다.
  - 서류 결과가 바뀔 때 그 날짜를 `docAt` 필드에 적는다(M5 원인 분석용, 화면 변화 없음).
- PM 결정: UX가 확인을 요청한 기준일은 14일로 정한다. 코드의 서류 발표 통상 간격(`STAGE_OFFSET_PRESETS`, 14일)과 같은 값이고, 지금 카드 경고가 쓰는 3일 기준은 아직 발표 전인 공고까지 잡아 경고가 늘어난다.

**B03 형태 미상·관심·제보 공고가 조건에 가려지지 않게**
- 스토리: 기업 형태를 골라 둔 지원자로서, 형태 정보가 없는 공고(원티드·제보 등)도 보고 싶다. 그래야 스타트업 PM 공고를 놓치지 않는다.
- 수용 기준
  - 기업 형태가 빈 공고는 기업 형태 조건을 통과한다(직무 미상 공고와 같은 규칙).
  - 관심(별) 표시한 공고는 내 조건과 상관없이 목록과 '관심' 칩에 보인다.
  - 목록 위에 「기업 형태 정보가 없는 공고 n건도 함께 보여요」가 보이고, 내 조건 창의 「형태 정보가 없는 공고도 보기」로 끌 수 있다(UX 04 문서 B-1-7).
  - 고정 데이터와 QA 조건으로 확인했을 때 형태 미상 때문에 숨는 접수 중 공고가 0건이다. 수집 단계에서는 같은 회사의 다른 공고에 있는 형태 값으로 빈 값을 채운다.

**B04 자동 이동 안전장치**
- 스토리: 지원자로서, 내가 담은 회사의 기록이 내가 모르는 다른 회사 공고로 바뀌지 않기를 바란다.
- 수용 기준
  - 예상 공고와 실제 공고의 회사 이름(괄호·㈜·공백을 뺀 정규화 기준)이 같을 때만 기록을 옮긴다.
  - 회사 이름이 다르면 옮기지 않고, 내 지원에 "LG그룹 예상 일정의 실제 공고 후보: LG생활건강 · 연결 / 무시" 같은 제안을 보여 준다. 연결은 사용자가 고른다.
  - 옮길 때 사용자가 넣은 마감일과 메모를 지우지 않고, 원래 예상 공고 id를 기록에 적어 되돌릴 수 있게 한다.
  - 그룹 단위 예상(LG그룹, 카카오그룹)을 담은 시드로 새로고침했을 때 회사 이름이 바뀐 기록이 0건이다.

**B05 담은 예상 날짜에 '예상' 표시**
- 스토리: 지원자로서, D-day가 실제 공고 날짜인지 추정인지 바로 알고 싶다. 그래야 추정 날짜만 믿다가 늦지 않는다.
- 수용 기준
  - 담은 예상 공고의 마감과 '통상 간격'으로 채운 전형 날짜에 상단 줄·캘린더·주간 플래너·표에서 같은 '예상' 표시가 붙는다.
  - 안 담은 공고의 예상 마감은 상단 줄에서 뺀다(UX 04 문서 LS-11).
  - 예상 날짜는 D-day 뒤에 「예상」을 붙이고(「D-3 · 예상」) 칩 테두리를 점선으로 바꾼다. 예상 마감이 오늘이면 한 줄로 쓰는 곳은 「예상 마감 오늘 · 공고 확인」, 레일 칩처럼 큰 글자와 설명이 나뉘는 곳은 큰 글자 「오늘」과 설명 「예상 마감 · 공고 확인」으로 쓴다(UX 04 문서 B-3-3). QA는 레일 칩 문구가 이 형태인지 확인한다.
  - QA 시드에서 상단 줄의 예상 항목 4건에 모두 표시가 붙는다.

**B17 어두운 화면 로그인 입력칸·채운 버튼 글자 대비**
- 스토리: 어두운 화면 모드를 쓰는 사용자로서, 로그인할 때 입력한 글자가 보여야 한다.
- 수용 기준
  - 어두운 화면에서 로그인 입력칸의 글자와 배경 명도 대비가 4.5:1 이상이다. 공통 입력 스타일(274행)에 email·password 등 빠진 입력 형식을 더한다.
  - 테마별 채운 버튼의 글자 대비는 UX 04 문서의 계산표(A-14)와 수정 값을 따른다.
  - 어두운 화면 로그인 스크린샷으로 전후를 비교한다.

**B06 외부 링크 스킴 검사**
- 스토리: 제보 공고를 누르는 사용자로서, 링크가 안전한 웹 주소일 때만 열리기를 바란다.
- 수용 기준
  - 공고·제보·레이더·업데이트 기록의 링크는 http·https일 때만 `href`로 쓰고, 나머지는 링크 없이 글자로 보인다.
  - 제보 창에서 http·https가 아닌 주소는 올리기 전에 막고 이유를 보여 준다.
  - `javascript:`, `data:`, 앞뒤 공백·대소문자가 섞인 스킴이 모두 막히는지 단위 확인이 있다.

**B07 도움말·하단 문구·meta·README 정리**
- 스토리: 처음 쓰는 사용자로서, 도움말이 지금 화면과 같아야 따라 할 수 있다.
- 수용 기준
  - 도움말 7번과 meta description의 '이 브라우저에만 저장'을 계정 저장 설명으로 바꾼다. 하단 문구와 같은 내용이다.
  - 도움말 1번의 '내 조건' 위치를 ⋯ 메뉴로 고치고, 표 보기·채용 레이더·매칭 아카이브·현황표 붙여넣기를 한 줄씩 설명한다.
  - 이번에 고치는 문구는 해요체로 쓴다. README의 자동 갱신 시각을 워크플로와 맞추고, `.qbox`의 `--panel` 변수를 정의한다.
  - 문안은 UX 04 문서 B-7-4를 그대로 붙인다(지금 탭·메뉴 이름 기준, 도움말 패널 전체 해요체). B25가 같은 릴리스에 들어가지 않으면 문안의 「담기」를 「지원」으로 바꿔 붙인다. 개발 시간은 1시간 안쪽이다.

**B27 현황표 '정리' 기본 선택 해제**
- 스토리: 현황표를 붙여 넣는 지원자로서, 내가 고르지 않은 기록이 '반영'과 함께 바뀌지 않기를 바란다.
- 수용 기준
  - '정리' 칸은 선택되지 않은 상태로 열리고, 미리보기에 정리 대상 건수를 보여 준다. 사용자가 직접 선택했을 때만 '반영'에 포함한다(UX 04 문서 ST-01).
  - 보관함이나 제보 공고를 불러오지 못한 상태면 '정리' 칸을 보여 주지 않는다. 불러오지 못한 공고의 기록이 정리 대상으로 잘못 잡히기 때문이다.

**B28 불러오기 실패 때 빈 보드 저장 막기**
- 스토리: 지원자로서, 네트워크가 잠깐 끊긴 채 앱을 열어도 지금까지의 기록이 지워지지 않기를 바란다.
- 수용 기준
  - 계정 데이터를 불러오지 못하면 빈 보드로 시작하지 않는다. 「기록을 불러오지 못했어요 · 다시 시도」를 보여 주고, 다시 불러오기에 성공하기 전에는 저장 요청을 보내지 않는다.
  - 불러온 데이터에 빠진 항목이 있으면 기본값으로 채워 쓴다. `normalizeDb()`가 형식 문제로 빈 기본값을 돌려주는 경로를 없앤다.
  - e2e: 계정 데이터 조회 응답을 오류로 바꾸고 로그인한다. 내 조건 창이 뜨지 않고, `?sales=1`로 열거나 화면을 조작해도 `jobboard_data` 쓰기 요청이 0건이다(M9).

**B26 공유 기기에서 로그아웃 때 이 기기 사본 지우기**
- 스토리: 학교·도서관 PC에서 쓰는 지원자로서, 로그아웃한 뒤 다음 사람이 내 지원 기록과 자소서를 가져갈 수 없기를 바란다.
- 수용 기준
  - 이 기기의 사본 키를 사용자별로 나눈다(UX 04 문서 G-17). 로그아웃하면 대기 중인 저장을 먼저 끝내고, 성공하면 그 사용자의 사본을 지운다. 저장에 실패하면 로그아웃을 멈추고 「저장하지 못한 변경이 있어요 · 다시 시도」를 보여 준다.
  - 사용자 구분이 없는 예전 사본은 새 계정을 만들 때만 가져오기를 묻는다. 문구에는 담은 공고 수와 기록의 마지막 날짜를 넣는다(UX 04 문서 B-4 표 15번 문안을 confirm 문구로 먼저 쓰고, 선택 창은 B20과 함께). 이미 있는 계정으로 로그인하면 예전 사본은 묻지 않고 지운다.
  - 이 업데이트로 막지 못하는 경우: 업데이트 전에 공유 기기에서 로그아웃한 사람의 사본은 예전 사본과 구별되지 않는다. 그 기기에서 처음 새 계정을 만드는 사람에게 한 번 가져오기 안내가 뜰 수 있어, 안내 문구에 "다른 사람이 이 브라우저를 썼다면 옮기지 마세요"를 넣는다.
  - QA: QA 계정으로 기록 → 로그아웃 → 그 계정의 사본이 없는지 확인한다. 예전 형식 사본을 넣고 QA 계정으로 로그인하면 안내 없이 사본이 지워지는지 확인한다. 새 계정 경로는 계정 데이터 조회 응답을 빈 값으로 바꾸고 쓰기 요청을 막아 재현한다.

**B08 저장 상태 표시와 실패 안내**
- 스토리: 여러 기기에서 쓰는 지원자로서, 방금 고친 내용이 계정에 저장됐는지 알고 싶다.
- 수용 기준
  - 헤더에 '저장 중', '저장됨', '저장 실패 · 다시 시도' 중 하나가 보인다(UX 04 문서 B-5).
  - 업로드가 실패하면 한 번 자동으로 다시 시도하고, 그래도 실패하면 실패 표시와 '다시 시도' 버튼을 보여 준다.
  - 저장이 끝나지 않았거나 실패한 상태로 창을 닫으려 하면 브라우저 이탈 경고가 뜬다.
  - e2e: 네트워크 차단 → 실패 표시, 연결 복구 → 다시 시도 → '저장됨'.

**B25 '지원' 버튼을 '담기'로, 담은 뒤 화면 이동 없애기, 빼기는 되돌리기 토스트로**
- 스토리: 여러 공고를 연달아 모으는 지원자로서, 담을 때마다 다른 탭으로 넘어가지 않고, 버튼 이름만 보고 무슨 일이 생기는지 알고 싶다.
- 수용 기준
  - 버튼 이름은 UX 04 문서 B-8 용어 사전을 따른다. 목록 행과 영업/마케팅 모아보기는 「담기 / 담음」, 상세 창은 주 버튼 하나라 대상을 붙여 「내 지원에 담기 / 내 지원에서 빼기」, 카드는 「내 지원에서 빼기」, 표의 × 버튼 접근 이름은 「{회사} 내 지원에서 빼기」다.
  - 담은 뒤 화면은 그대로 있고 토스트 「{회사} · 내 지원에 담았어요 [내 지원 보기]」가 뜬다(UX 04 문서 LS-01).
  - 상세 창·카드·표 ×의 빼기는 모두 확인 창 없이 바로 빼고 「{회사} · 내 지원에서 뺐어요 [되돌리기]」 토스트를 띄운다(UX 04 문서 B-4 표 3·4번). 기록 내용은 그대로라 되돌리면 같은 상태로 돌아온다.
  - 토스트의 버튼 기능은 B10 '오늘' 화면의 결과 기록 토스트와 같이 쓴다.

**B09 빈 기록 저장 제외**
- 스토리: 지원자로서, 저장이 빠르고 휴대폰 데이터를 덜 쓰기를 바란다.
- 수용 기준
  - localStorage와 Supabase에 쓰는 사본에서만 빈 기록을 뺀다. 화면이 들고 있는 메모리 속 기록 객체는 지우지 않는다(지우면 그 객체에 이어지는 별 표시 같은 변경이 사라진다).
  - '빈 기록'은 모든 필드가 `app()`이 만드는 기본값과 같은 기록이다. 관심, 메모, 자소서, 전형, 미지원 표시, 접힘, 공고 수정값 중 하나라도 있으면 저장한다.
  - QA 시드와 주인 백업 사본(로컬, 비공개)으로 확인했을 때 비어 있지 않은 기록 수가 정리 전후 같다.
  - 첫 화면을 그린 뒤 업로드 본문의 기록 수가 실제 기록 수와 같다(e2e로 요청 본문 확인).

**B10 첫 화면 '오늘' (실험 1 변형 B)**
- 스토리: 로그인한 지원자로서, 오늘 처리할 마감·밀린 결과·이번 주 일정을 첫 화면에서 보고 싶다.
- 수용 기준
  - `?v=b1`일 때만 '오늘' 탭이 맨 앞에 생기고 로그인 직후 선택된다. 파라미터가 없으면 현행과 같다.
  - 화면 구성과 문구는 UX 04 문서 B-2를 반나절 범위로 줄인 03 문서의 실험 1 변형 B 정의를 따른다.
  - '결과 확인 필요' 블록의 [서류 합격]·[탈락] 버튼은 표 보기 상태 변경과 같은 함수로 기록한다.
  - 저장 형식에 새 필드를 만들지 않는다(UX B-2의 `snooze`는 실험 결과가 B 채택일 때 붙인다).

**B11 공고 데이터 기준일 안내**
- 스토리: 지원자로서, 공고 데이터가 오래됐으면 알고 싶다.
- 수용 기준
  - `jobs.json`의 updated가 오늘보다 2일 넘게 이전이면 목록 위에 "공고 데이터가 n일 전 기준이에요" 안내가 보인다.
  - 안내는 닫을 수 있고 같은 날에는 다시 뜨지 않는다.

**B12 목록 계산 사전 처리**
- 스토리: 휴대폰 사용자로서, 별이나 담기를 누를 때 화면이 바로 반응하기를 바란다.
- 수용 기준
  - 실제 공고의 회사 키를 한 번만 계산해 집합으로 만들고 `superseded()`는 그 집합을 조회한다.
  - 고정 데이터로 보이는 공고 목록이 바꾸기 전과 같다.
  - 모바일 에뮬레이션에서 `renderAll()` 시간을 전후로 재서 기록한다(M7).

**B13 표 보기 전형 날짜·시각 입력, 단계 목록 통일**
- 스토리: 면접 일정을 받은 지원자로서, 표에서 바로 날짜와 시각을 넣고 싶다.
- 수용 기준
  - 진행 단계가 서류 제출 다음 단계이면 그 단계의 날짜·시각 칸이 표에 보인다. 휴대폰 표 보기에서도 같다.
  - 넣은 시각이 상단 줄·캘린더·주간 플래너에 함께 나온다.
  - 표의 단계 목록에 카드의 전형 이름(AI 역량검사·적성검사·GSAT·필기전형 등)이 들어가 순서가 어긋나지 않는다.

**B14 담기와 제출 분리 (실험 2 변형 B)**
- 스토리: 공고를 일단 모으는 지원자로서, 담은 것과 실제로 낸 것을 나눠 보고 싶다.
- 수용 기준
  - `?v=b2`일 때만 03 문서의 실험 2 변형 B 문구와 동작이 켜진다.
  - 기존 기록(제출 표시 필드가 없는 기록)은 지금과 같은 상태로 해석한다.
  - B16의 상태 타일에서는 '제출 전'이 '마감 전' 자리를 대신한다. 표의 상태를 '제출 전'·'미지원' 밖의 값으로 바꾸거나 서류 결과를 합격·탈락으로 바꾸면 제출한 것으로 본다(03 문서 3.3, UX 04 문서 B-3-1).
  - 상단 줄은 '제출 전' 공고의 서류 마감만 보여 준다.

**B15 휴대폰 첫 화면·'?' 버튼·표 칸 겹침 정리**
- 스토리: 휴대폰 사용자로서, 첫 화면에서 공고를 더 많이 보고 싶다.
- 수용 기준
  - 필터 칩을 한 줄 가로 스크롤로 바꿔 390px 폭 첫 화면에 공고 카드가 3개 이상 보인다(UX 04 문서 B-6의 목표는 4장).
  - '?' 버튼이 카드의 버튼과 글자를 가리지 않는다.
  - 휴대폰 표 보기에서 빈 칸 표시가 칸 이름과 겹치지 않고 날짜 칸이 잘리지 않는다.

**B16 표·카드 상태 모델과 요약 숫자 통일**
- 스토리: 지원자로서, 보기 방식을 바꿔도 같은 숫자를 보고 싶다.
- 수용 기준
  - 표와 카드가 같은 상태 판정 함수로 센다(UX 04 문서 B-3-1).
  - 표 타일은 B-3-1의 흐름 순서(전체 · 마감 전 · 결과 대기 · 확인 필요 · 합격·진행 · 탈락)로 바꾼다. 실험 2는 이 타일을 전제로 한다(03 문서 3.1).
  - 서류 합격률은 한 가지 정의를 쓰고, 정의를 숫자 옆 설명으로 보여 준다.

**B18 탭 상태 주소 반영**
- 스토리: 지원자로서, 새로고침해도 보던 탭에 머물고 싶다.
- 수용 기준
  - 탭을 바꾸면 주소에 해시가 붙고, 그 주소로 열면 그 탭이 열린다. 형식은 UX 04 문서 B-1-8 표의 '지금 탭' 열을 따른다(예: 캘린더 `#/schedule/month/…`, 매칭 아카이브 `#/jobs/match`). 그래서 탭 개편 뒤에도 주소를 바꿀 필요가 없다.
  - `?sales=1`·`?mkt=1`·`?v=` 파라미터와 함께 써도 동작하고, 해시를 바꿀 때 `?v=`를 지우지 않는다.

**B19 일정 내보내기 진입점 노출**
- 스토리: 휴대폰 캘린더로 알림을 받는 지원자로서, 일정을 넣은 자리에서 바로 캘린더로 보내고 싶다.
- 수용 기준
  - 내 지원 화면과 전형 날짜를 넣은 직후 '휴대폰 캘린더에 넣기'가 보인다.
  - 기존 ⋯ 메뉴의 일정 내보내기와 같은 파일을 만든다.

**B20 자주 쓰는 prompt 3곳을 화면 안 입력칸으로**
- 스토리: 휴대폰·인앱 브라우저 사용자로서, 시스템 입력창 대신 화면 안에서 입력하고 싶다.
- 수용 기준
  - 할 일 추가·행 추가·전형 직접 입력이 화면 안 입력칸으로 바뀐다(UX 04 문서 B-4). Enter로 저장, Esc로 취소된다.

1. Must 항목을 합친 뒤 QA 회귀 확인: 로그인·로그아웃, 전체 공고, 내 지원(표·카드), 캘린더, 주간 플래너, 제보, 백업·복원, 현황표 붙여넣기, 불러오기 실패 흉내(M9).
