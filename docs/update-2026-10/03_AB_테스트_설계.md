## 1. 공통 준비

### 1.1 변형 전환

같은 빌드에서 주소 파라미터로 바꾼다. 앱은 이미 `?sales=1`·`?mkt=1`로 화면을 켜는 코드를 쓰고 있어 같은 방식을 따른다.

| 주소 | 변형 |
|---|---|
| 파라미터 없음, `?v=a` | 현행(A). 일반 사용자는 언제나 이 상태다 |
| `?v=b1` | 실험 1의 B |
| `?v=b2` | 실험 2의 B |

```js
/* 실험 변형: ?v=a | b1 | b2. 이 탭(세션) 동안 유지하고, 값이 없으면 a(현행). */
const VARIANT = (function(){
  let v = new URLSearchParams(location.search).get("v");
  try {
    if(v) sessionStorage.setItem("jb-variant", v);
    else v = sessionStorage.getItem("jb-variant");
  } catch(e) {}
  return v === "b1" || v === "b2" ? v : "a";
})();
document.documentElement.dataset.variant = VARIANT;   // 스크린샷·로그에서 변형 확인용
```

- 두 실험의 B를 함께 켜지 않는다(`b1`과 `b2`는 서로 배타).
- 변형 코드는 `VARIANT === "b1"` 같은 조건 안에만 넣는다. 파라미터 없는 접속에서 B 요소가 하나라도 보이면 출시 차단 결함으로 본다(02 문서 R5).
- 저장 데이터: 실험 1은 새 필드를 만들지 않는다. 실험 2는 `sent`·`sentAt` 두 필드를 더할 뿐 기존 필드를 바꾸지 않고, A는 이 필드를 읽지 않는다.
- 설정 토글(선택): 휴대폰 실기기에서 주소를 바꾸기 어려우면, 주인 계정에만 보이는 ⋯ 메뉴 항목으로 같은 세션 값을 쓴다. 이번 패널은 Playwright로 돌리므로 필요 없다.

### 1.3 실측 지표와 측정 도구

앱 코드를 고치지 않고 Playwright가 페이지에 측정 스크립트를 넣는다. 역할극 에이전트가 무엇을 누르든 스크립트가 따로 센다.

```js
// tests/e2e/panel/measure.mjs (스케치)
export async function instrument(page){
  await page.addInitScript(() => {
    const log = window.__panel = { clicks: 0, deadRun: 0, deadBursts: 0, views: [], dialogs: [] };
    const interactive = "button, a, input, select, textarea, summary, label, [role=tab], [role=menuitem]";
    document.addEventListener("click", e => {
      log.clicks++;
      if(e.target.closest(interactive)){ log.deadRun = 0; return; }
      log.deadRun++;
      if(log.deadRun === 3) log.deadBursts++;          // 누를 수 없는 곳을 연달아 3번
    }, true);
    const watch = () => {
      const v = document.querySelector("section.view:not([hidden])");
      if(v && log.views[log.views.length - 1] !== v.id) log.views.push(v.id);
      document.querySelectorAll("dialog").forEach(d => {
        if(d.open && !d.dataset.seen){ d.dataset.seen = "1"; log.dialogs.push(d.id); }
        if(!d.open) delete d.dataset.seen;
      });
    };
    new MutationObserver(watch).observe(document, { subtree: true, attributes: true, attributeFilter: ["hidden", "open"] });
  });
}
// 되돌아가기: 과제 안에서 이미 지난 화면이 다시 나온 횟수
export const backtracks = views => views.filter((v, i) => views.indexOf(v) < i).length;
// 과제 성공 판정: 저장 데이터를 직접 읽는다
export const readDb = page => page.evaluate(() => JSON.parse(localStorage.getItem("jobboard-v2")));
```

| 지표 | 정의 | 구분 |
|---|---|---|
| 클릭·탭 수 | 과제 시작부터 성공 조건을 채울 때까지 문서에서 일어난 click 이벤트 수. 글자 입력은 세지 않고, 날짜 칸에 값을 넣는 동작은 1회로 센다 | 실측 |
| 화면 전환 수 | 보이는 화면(`section.view`)이 바뀐 횟수 + 열린 다이얼로그 수 | 실측 |
| 막힘 | 되돌아가기 횟수 + 헛클릭 묶음 수(누를 수 없는 곳을 연달아 3번 누른 묶음) | 실측 |
| 완료 | 성공 조건을 저장 데이터(localStorage `jobboard-v2`) 또는 진행자 기록으로 판정. 클릭 40회나 5분을 넘기면 실패 | 실측 |
| 정확도 | 과제가 끝났을 때 정답과 같은 상태인 항목 수(실험 2) | 실측 |
| 소요 시간 | 역할극 에이전트의 시간이라 판정에 쓰지 않고 참고로만 적는다 | 참고 |

### 1.4 주관 지표 (역할극 응답)

과제마다 바로 묻는다. 두 변형을 모두 마친 뒤 선호를 묻는다.

| 지표 | 질문 | 척도 |

| 쉬움 | "방금 과제는 얼마나 쉬웠나요?" | 1 매우 어려움 ~ 5 매우 쉬움 |

### 1.5 패널 운영

- **패널원**: 01 문서의 페르소나 카드(프로필, 현재 대안, 가장 큰 불편, 인용)를 역할극 지침으로 받은 가상 사용자다. AI 에이전트가 Playwright로 브라우저를 조작하며, 화면 스크린샷과 접근성 트리를 보고 다음 행동을 고른다. 팀원이 역할을 맡아 직접 조작해도 같은 기록 방식을 쓴다.
- **눈가림**: 패널원에게 이 문서의 가설·판정 규칙·변형 이름을 보여 주지 않는다. 지시문만 받는다.
- **진행자**: QA가 맡는다. 변형을 설계한 PM은 진행하지 않는다. 진행자는 지시문만 읽고 힌트를 주지 않는다.
- **순서 효과**: 5명 중 3명은 A → B, 2명은 B → A 순서로 한다. 두 번째 변형에서는 회사 이름·날짜만 바꾼 평행 시드(′ 표시)를 써서 앞 과제의 기억이 이어지지 않게 한다.
- **규모**: 실험마다 5명 × 2변형 × 4과제 = 40회 과제 수행.

## 2. 실험 1 — 로그인 후 첫 화면: 공고 목록(A) vs '오늘'(B)

### 2.1 가설

- **If** 로그인 직후 첫 화면을 공고 목록 대신 '오늘'(내 마감, 결과 확인 필요, 이번 주 전형, 새로 뜬 공고)로 보여 주면,
- **Then** '오늘 챙길 일 찾기', '밀린 결과 기록', '이번 주 전형 확인' 과제의 클릭·화면 전환·막힘이 줄고 완료가 늘며, 새 공고를 찾아 담는 과제는 나빠지지 않는다.
- **Because** 지금은 밀린 결과 경고와 다가오는 일정이 카드 보기에만 있어(02 문서 F8) 사용자가 탭과 보기를 오가야 하고, 사용자는 앱을 열면 먼저 오늘 할 일을 찾는다(H4, 가상 인터뷰에서 나온 가설).

### 2.2 변형 정의

**A — 공고 목록 시작(현행 기준)**
- 로그인 직후 전체 공고 탭(접수 중 필터, 마감 순)이 열린다. 헤더 아래 D-day 줄이 있다.
- 이번 릴리스의 Must·Should(02 문서 5장)가 들어간 상태를 기준으로 한다. '확인 필요' 자동 판정(B02), 예상 표시(B05), '담기' 문구(B25)는 A와 B에 똑같이 들어간다.
- UX 04 문서 B-1(탭 개편)이 들어가면 A·B 모두 새 탭 위에서 비교한다. 이번 릴리스에서는 탭이 지금과 같다.
- 근거 화면: `desk-list.png`, `mob-list-fold.png`.

**B — '오늘' 시작 (`?v=b1`, UX 04 문서 B-2를 반나절 범위로 줄인 판)**
- 탭 줄 맨 앞에 '오늘' 탭이 생기고 로그인 직후 선택된다. 헤더 아래 D-day 줄은 숨긴다(B-2와 같다. 같은 정보를 '오늘'이 보여 준다).
- 머리: 「10월 14일 수요일」과 요약 한 줄 「마감 n건 · 결과 확인 n건 · 이번 주 전형 n건」. 0인 항목은 빼고, 모두 0이면 「오늘 챙길 일정이 없어요.」
- 블록 4개를 한 단으로 쌓는다(데스크톱도 한 단).

### 2.7 판정 규칙 (실행 전에 고정)

1. 실측 지표는 패널원별로 E1-T1~T3를 합한 값을 구하고, 5명의 중앙값(막힘은 합계)을 A와 B로 비교한다.
2. 지표별 우위 기준. 차이가 기준보다 작으면 '같음'이다.

| 지표 | B 우위 | B 열세 |
|---|---|---|
| ① 클릭·탭 수 중앙값 | A보다 3회 이상 적음 | A보다 3회 이상 많음 |
| ② 화면 전환 수 중앙값 | 2회 이상 적음 | 2회 이상 많음 |
| ③ 막힘 합계 | 2회 이상 적음 | 2회 이상 많음 |
| ④ 완료 수(15개 중) | 2개 이상 많음 | 2개 이상 적음 |

3. 가드레일 위반: 아래 중 하나라도 있으면 B를 채택하지 않는다.
   - E1-T4 클릭 중앙값이 A보다 2회 넘게 많다.
   - A에서 완료한 과제를 B에서 실패한 패널원이 있다.
   - 콘솔 오류가 1건 이상이거나, 다른 공고에 결과를 적은 기록이 1건 이상이다.
   - 첫 화면 `renderAll()` 시간이 A보다 50ms 넘게 늘었다.
4. 결정
   - **B 채택**: ①~④ 중 2개 이상 B 우위, B 열세 0개, 가드레일 위반 없음. UX B-2 전체를 다음 릴리스 후보로 올리고, 시작 화면 기본값 변경은 주인 확인 뒤에 한다.
   - **보류**: 실측은 B 채택 조건을 채웠는데 선호에서 5명 중 3명 이상이 A를 골랐다. 반복된 혼란 지점을 고친 B′로 한 번 더 돌린다.
   - **A 유지**: 그 밖의 경우. 기준에 걸리지 않는 애매한 결과도 A 유지다(바꾸는 쪽이 근거를 갖춰야 한다).

## 3. 실험 2 — 담기와 제출: 한 단계(A) vs 두 단계(B)

### 3.1 전제

- 02 문서 B25('담기' 문구, 담은 뒤 화면 이동 없음)가 들어간 빌드에서 돌린다. 그러면 두 변형의 차이가 '제출 표시 단계' 하나로 좁혀진다.
- B25 전에 돌리면 A는 '지원' 문구와 자동 이동을 가진 현행이 되어 B와의 차이가 문구, 화면 이동, 제출 단계로 늘어난다. 이때는 B가 이겨도 어느 요소 덕인지 가를 수 없으므로 보고서에 '묶음 비교'라고 적는다.
- 상태 표시는 02 문서 B16(UX 04 문서 B-3-1의 상태 모델과 타일)이 들어간 빌드를 기준으로 한다. B16 없이 돌려야 하면 B의 '제출 전' 타일을 지금 타일 맨 앞에 더하고, 보고서의 한계 칸에 그 차이를 적는다.

### 3.2 가설

- **If** 담은 공고가 '제출 전' 상태로 시작하고, 사용자가 [제출했어요]를 눌러야 '결과 대기'로 넘어가게 하면,
- **Then** 마감이 지난 공고를 정리하는 과제의 정확도가 오르고, 아직 내야 할 마감을 찾는 과제가 짧아진다. 그 대가로 제출을 적는 과제의 클릭은 패널원별 3회 넘게 늘지 않는다.
- **Because** 지금은 담는 순간 '대기 · 서류 제출'로 기록돼 낸 공고와 안 낸 공고가 화면에서 구분되지 않고(02 문서 F10), 사용자는 나중에 기억으로 가려낸다(H1, 가상 인터뷰에서 나온 가설). 낸 날 바로 적게 하면 그 정보가 기억 대신 화면에 있다.

### 3.3 변형 정의

**A — 한 단계 (B25·B16이 들어간 기본 빌드)**
- 담으면 서류 결과 '대기', 진행 단계 '서류 제출'로 기록된다. B-3-1 화면에서는 마감 전이면 '마감 전'(D-day 칩), 마감이 지나면 '결과 대기'로 보인다.
- 상단 D-day 줄은 결과가 '대기'인 담은 공고의 서류 마감을 모두 보여 준다.
- 냈다는 사실을 적으려면 메모 칸을 쓰는 수밖에 없다.

**B — 두 단계 (`?v=b2`)**

| 위치 | A | B |
|---|---|---|
| 전체 공고·상세 창의 담기 | 목록 행 「담기 / 담음」, 상세 창 「내 지원에 담기 / 내 지원에서 빼기」(B25) | 같음 |
| 담은 직후 상태 | '대기', 진행 단계 '서류 제출' | '제출 전'. 진행 단계 칸은 비활성 |
| 내 지원 표 | 상태 선택 | 상태 선택지 맨 앞에 '제출 전'. 제출 전인 행의 상태 칸 옆에 [제출했어요] |
| 내 지원 타일 | B-3-1 타일: 전체 · 마감 전 · 결과 대기 · 확인 필요 · 합격·진행 · 탈락 | '마감 전' 자리를 '제출 전'이 대신한다. [제출했어요]를 누른 공고는 마감 전이어도 '결과 대기'에 들어간다 |
| 상태 표시 우선순위 | 확인 필요 > 탈락 > 합격·진행 > 마감 전 > 결과 대기 > 미지원 | 확인 필요 > 탈락 > 합격·진행 > 제출 전 > 결과 대기 > 미지원 |
| 카드 보기의 서류 단계 | 서류 결과 선택(대기·합격·불합격) | 제출 전이면 그 자리에 「아직 내지 않았어요」와 [제출했어요] |

| 상세 창 | 내 지원에 담기 / 내 지원에서 빼기 | 같음. 담은 뒤 제출 전이면 [제출했어요]를 더한다 |
| 내 지원 머리 설명 | B07·B25 문구 | 「담은 공고가 모여요. 서류를 냈으면 '제출했어요'를 눌러 주세요.」 |
| 마감이 지난 '제출 전' | 해당 없음 | 상태 칩 「제출 전 · 마감 지남」. 낸 적이 없으니 '확인 필요' 자동 판정에서 뺀다 |
| [제출했어요]를 누른 뒤 | — | 토스트 「{회사} · 제출했다고 적었어요 [되돌리기]」 |

- 데이터: `apps[id].sent`(true/false), `apps[id].sentAt`(YYYY-MM-DD). B에서 담으면 `sent: false`, [제출했어요]를 누르면 `sent: true`와 그날 날짜. `sent`가 없는 기존 기록은 제출한 것으로 본다(현행과 같은 의미). 상태 판정은 '담음이고 `sent === false`면 제출 전'이다. 표의 상태 선택에서 '제출 전'과 '미지원' 밖의 상태를 고르면 `sent: true`, '제출 전'을 고르면 `sent: false`로 바꾼다. 서류 결과를 합격·탈락으로 바꿔도 `sent: true`로 본다(결과가 왔다면 낸 것이다). A는 이 필드를 읽지 않는다.
- 구현 메모(반나절): 담기 버튼에서 `sent = false`, `tStatus()`·`setTStatus()`에 '제출 전' 분기와 `sent` 갱신, 표 행 버튼, 타일 하나, `renderRail()` 필터 한 줄, 상세 창 버튼, 카드의 서류 단계 분기, 내 지원 머리 문구, '확인 필요' 판정 예외 한 줄.

### 3.6 과제 시나리오

| 과제 | 시작 상태 | 지시문 (S2 기준) | 성공 조건 |
|---|---|---|---|
| E2-T1 여러 공고 담기 (가드레일) | 전체 공고 탭, 접수 중 필터 | "오늘 마감인 공고 중 직무에 기획/전략이 있는 공고 3개를 담은 뒤, 내 지원에서 세 개가 들어갔는지 확인해 주세요." | 조건에 맞는 공고 3건이 담기고, 내 지원 화면을 한 번 이상 봄 |
| E2-T2 제출 적기 (비용) | 내 지원 탭. S-OIL·삼립·삼천리가 담긴 상태 | "S-OIL과 삼립은 오늘 오후에 냈고, 삼천리는 내지 않기로 했어요. 지원 보드에 그대로 적어 주세요." | A: S-OIL·삼립은 담긴 상태(미지원 아님), 삼천리는 미지원. B: S-OIL·삼립 `sent: true`, 삼천리는 미지원 |
| E2-T3 마감 지난 공고 정리 (정확도) | 내 지원 탭. 패널원이 기억 카드를 받음 | "기억 카드를 보고, 마감이 지난 공고들을 실제 상황과 같게 정리해 주세요." | 6항목이 각각 정답과 같으면 1점(0~6점) |
| E2-T4 아직 낼 마감 찾기 (정보) | 로그인 직후 첫 화면 | "아직 내지 않아서 마감 전에 내야 하는 공고를 모두 찾아 말해 주세요." | 정답 4개(현대자동차그룹, 신한라이프, 가상 스타트업 A, 마드라스체크(플로우))를 모두 말하고 틀린 공고를 넣지 않으면 성공 |

해석 주의: E2-T3와 E2-T4는 A에 제출 여부를 적는 자리가 없다는 차이를 재도록 짜여 있어 B에 유리하다. 그 대가는 E2-T1·E2-T2의 클릭으로 잰다. 판정은 둘을 함께 본다. B에서 E2-T3의 '제출 전 그대로'를 정답으로 받는 것도 같은 이유다. 낸 날 [제출했어요]를 누르는 비용은 E2-T2에서 이미 센다.

### 3.7 패널 구성

| 패널원 | 기기 | 순서 | 넣은 이유 |
|---|---|---|---|
| P1 김지윤 | 데스크톱 | A → B | 노션에 '지원 예정'이 쌓인 사례. 담기와 제출이 섞이는 유형(H1) |
| P2 박도현 | 휴대폰 | B → A | 휴대폰에서 연달아 담고, 제출 사실은 카톡에 따로 적는 유형 |
| P3 이서진 | 데스크톱 | A → B | '지원' 문구를 제출로 이해한 사례(01 문서 P3 T1) |
| P5 정하은 | 데스크톱 | B → A | 노션 템플릿에서 '제출' 상태를 따로 쓰는 유형. 두 단계 방식에 익숙한 쪽이 느끼는 비용 |
| P6 윤태오 | 데스크톱 | A → B | '지원함' 체크와 실제 제출이 달라 '제출일' 칸을 만든 사례 |

P4 최민재는 뺐다. 원티드에서 바로 지원해 담기와 제출 사이 간격이 거의 없다.

### 3.8 판정 규칙 (실행 전에 고정)

1. 지표별 우위 기준. 차이가 기준보다 작으면 '같음'이다.

| 지표 | B 우위 | B 열세 |
|---|---|---|
| ① E2-T3 정확도 합계(30점) | A보다 3점 이상 높음 | 3점 이상 낮음 |
| ② E2-T4 성공 수(5명) | 2명 이상 많음 | 2명 이상 적음 |
| ③ E2-T4 클릭 중앙값 | 2회 이상 적음 | 2회 이상 많음 |
| ④ 막힘 합계(전체 과제) | 2회 이상 적음 | 2회 이상 많음 |
| ⑤ 비용: E2-T2 클릭 중앙값 | — | A보다 3회 넘게 많음 |

2. 가드레일 위반: 아래 중 하나라도 있으면 B를 채택하지 않는다.
   - E2-T1 클릭 중앙값이 A보다 2회 넘게 많다.
   - `sent`가 없는 기존 기록이 B에서 '제출 전'으로 보인 경우가 1건 이상이다.
   - 상단 줄에서 '제출 전' 마감이 빠진 경우가 1건 이상이다.
   - 콘솔 오류가 1건 이상이다.
3. 결정
   - **B 채택**: ①~④ 중 2개 이상 B 우위, ①~⑤에서 B 열세 0개, 가드레일 위반 없음. B14를 기본값으로 올리는 안을 다음 릴리스 범위 회의에 낸다. 기존 데이터는 `sent`가 없으면 제출로 보므로 따로 옮길 필요가 없다.
   - **보류**: 우위 조건은 채웠는데 ⑤에서 열세다. 담은 직후 토스트에 [제출했어요]를 넣는 식으로 비용을 줄인 B′로 한 번 더 돌린다. 선호에서 5명 중 3명 이상이 A를 고른 경우도 보류다.
   - **A 유지**: 그 밖의 경우.

## 7. 이 설계의 한계와 편향 줄이기

- 역할극 응답은 페르소나를 만든 팀의 가정을 따라가기 쉽다(확증 편향). 그래서 판정은 실측 지표로 하고, 주관 지표는 '보류' 조건에만 쓴다.
- 변형 설계자(PM)와 진행자(QA)를 나누고, 패널원에게 가설·판정 규칙·변형 이름을 보여 주지 않는다.
- 실측 값은 패널원이 고른 경로의 길이다. 실제 사람의 망설임, 오타, 주의 분산은 일부만 들어간다.
- 5명은 통계 표본으로 쓰지 않는다. 중앙값과 합계는 판정 규칙을 적용하기 위한 요약이다.
- 학습 효과는 순서 교차와 평행 시드로 줄인다. 그래도 줄지 않는 효과는 보고서의 한계 칸에 적는다.
- 실험 2의 일부 과제는 구조상 B에 유리하다(3.6 해석 주의). 비용 지표 ⑤와 함께 판정한다.
- 결과를 실제 사용자 효과로 옮겨 말하지 않는다. 실제 효과는 배포 뒤 02 문서 M5(결과 미입력 비율)와 ①-b 집계로 확인하고, 이벤트 기록 테이블(B22)이 생기면 변형별 실제 사용을 비교한다.
