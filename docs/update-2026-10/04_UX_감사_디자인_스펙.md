# 지원 보드 2026-10 업데이트 · 04 UX 감사와 디자인 스펙

- 담당: UX/UI · 작성일 2026-10-14 (KST)
- 대상 코드: `index.html` (main `a6d2ff3`, 라이브 9/17 빌드보다 새 버전). 이 문서의 줄 번호(L)는 모두 이 커밋 기준이다.
- 근거 화면: 팀 작업 폴더의 `qa/before/` 스크린샷(`desk-*` 1280px, `mob-*` iPhone 14, `*-dark` 어두운 화면)과, 이 문서를 위해 추가로 찍은 `ux/shots/`(`login-*` 로그인, `new-*` 신규 사용자 재현, `desk-share`, `desk-focus-6`). 표의 근거 칸에는 확장자 `.png`를 뺀 파일 이름만 적는다. 스크린샷은 저장소에 넣지 않는다.
- 측정 방법: Playwright(Chromium)로 데스크톱 1280×900, 휴대폰은 iPhone 14 프로필(뷰포트 390×664)에서 쟀다. QA 계정으로 읽기만 했고 서버 쓰기 요청은 가로채서 막았다. 신규 사용자 화면은 계정 데이터 조회 응답을 빈 값으로 바꿔 재현했다. 명도 대비는 CSS 변수의 실제 색상값으로 WCAG 2.x 공식에 따라 계산했다.
- 이번 단계는 감사와 설계까지다. 구현은 개발 담당이 맡고, 스펙마다 이유(왜)와 난이도를 붙였다. 난이도 기준: **S** CSS·문구 수정이나 함수 한두 개(반나절 안), **M** 새 컴포넌트 하나 또는 여러 화면 연결(1~2일), **L** 화면 구조나 데이터 흐름 변경(3일 이상).

## 0. 요약

1. 어두운 화면에서 로그인 입력칸 글자가 보이지 않는다(흰 배경에 밝은 글자, 1.17:1). 채운 버튼의 흰 글자도 여섯 테마 모두 2.2:1 이하다. 이번 배포 전에 고쳐야 하는 유일한 심각도 4 묶음이고, CSS 토큰 몇 줄로 끝난다.
2. 밝은 화면도 보조 글자색(`--muted`, 3.52:1)과 상태 칩 글자(접수 중 3.99:1, 대기 4.34:1)가 기준 미달이다. 색 계열을 유지한 채 값만 조정하는 안을 B-3·B-9에 적었다.
3. 같은 상태를 화면마다 다른 말과 색으로 보여 준다. 내 지원 표는 「탈락」을 빨강, 카드는 「불합격」을 회색으로 쓰고, 합격 색은 테마를 따라 바뀐다. 상태 판정 하나, 칩 문구 규칙 하나, 테마와 분리한 상태 색 토큰으로 정리했다(B-3).
4. 내비게이션은 공고를 보는 화면(전체 공고, 채용 레이더, 영업·세일즈, 마케팅, 매칭)이 1차 탭으로 흩어져 있고, 메뉴는 설정·기능 켜기·데이터·계정이 한 줄로 섞여 있다. 1차 탭을 「(오늘) · 공고 · 내 지원 · 일정 · 내 문서」로 줄이고 주소 해시로 현재 화면을 유지하는 안을 냈다(B-1). 02 문서는 탭 개편을 다음 릴리스로 미루고, 주소 해시는 시간이 남으면 넣는 범위(B18)로 정했다.
5. 휴대폰 전체 공고는 첫 화면에 카드가 1장만 온전히 보이고, 접수 중 57건이 8,692px(3배 해상도 스크린샷 26,076px)로 이어진다. 마감 구간 묶음과 「더 보기」, 높이 96px 이하 카드, 머리 영역 축소로 첫 화면 4장 이상, 첫 렌더 약 3,100px를 목표로 한다(B-6).
6. 처음 가입한 사람은 설명 없이 「내 조건」 창을 먼저 보고, 닫으면 숫자 0 타일과 남의 공고 마감 칩만 보인다. 3단계 첫 사용 흐름과 화면별 빈 상태 문구를 B-7에 정리했다.
7. 문구는 합쇼체 평서문 약 94문장과 해요체 평서문 약 47문장이 섞여 있다. 해요체로 통일하고, 「지원/지원하기/지원 담기/지원 취소」처럼 같은 동작을 부르는 말을 「담기/빼기」로 묶는 용어 사전과 교체표를 만들었다(B-8). 이번 릴리스는 바뀌는 문구만 해요체로 쓰고, 도움말 문안은 지금 탭 이름으로 따로 준비했다(B-7-4).
8. 「오늘」 대시보드(B안)는 내 마감 → 결과 확인 필요 → 이번 주 전형 → 오늘 할 일 → 새로 뜬 공고 순서로 설계했다. 실사용에서 밀리는 결과 기록을 한 번 누르기로 끝내는 버튼을 넣었다(B-2). 실험 1은 03 문서의 축소판(`?v=b1`)으로 먼저 돌린다.

## 1. 가정

1. 주 사용자는 신입·인턴 지원자이고 휴대폰과 노트북을 함께 쓴다. 휴대폰은 마감 확인과 결과 기록, 노트북은 공고 탐색과 자소서 작성에 주로 쓴다고 본다.
2. 핵심 흐름은 브리핑의 해석대로 「접수 중 공고 찾기 → 담기 → 마감 D-day 확인 → 결과 기록」이다. 자소서 편집기·아카이브·전형 트랙은 유지하되 화면 앞에 내세우지 않는다.
3. A/B 실험의 변형 정의와 지표는 03 문서를 따른다. 실험 1의 A는 지금 탭 구조에서 공고 목록으로 시작하고, B(`?v=b1`)는 탭 맨 앞에 「오늘」을 더한다. 실험 2는 B-3-1 상태 모델이 들어간 빌드가 A, 「제출 전」 단계를 더한 것이 B(`?v=b2`)다.
4. 데이터 모델 필드는 바꾸지 않는 것을 기본으로 한다. 새로 필요한 값(결과 입력 미루기 날짜 `snooze`, 첫 사용 진행 `profile.onboard`)은 선택 필드로 더한다. 실험 2 B의 `sent`·`sentAt`은 03 문서 3.3이, 서류 결과를 바꾼 날짜 `docAt`은 02 문서 B02가 정의한다. 내부 값 `불합격`, `확인필요` 같은 키는 그대로 두고 화면 문구만 바꾼다.
5. 「확인 필요」 자동 판정은 02 문서 B02에서 확정했다. 발표 예정일이 있으면 그 날짜, 없으면 서류 마감 후 14일(코드의 `STAGE_OFFSET_PRESETS` 서류 발표 간격과 같은 값)이 기준이다. 카드 보기의 기존 경고(마감 3일 뒤)도 같은 판정으로 바꾼다. 전형 단계로 넓히는 7일 기준은 다음 릴리스 제안이고 아직 임시값이다.
6. 계정 전용 표시 기능은 이 문서 범위 밖이다.
7. 스크린샷의 날짜 입력칸이 `09/21/2026`처럼 보이는 것은 테스트 브라우저 언어 설정 때문이라 문제로 잡지 않았다. 한국어 브라우저에서는 `2026. 09. 21.`로 보인다.
8. 스크린샷마다 데이터 시점이 조금씩 다르다(QA가 시드를 다시 넣은 시점 차이). 건수가 화면마다 다른 것은 문제로 잡지 않았다.

### A-16 정보 구조(IA) 비평

**지금 구조**

```
헤더   로고 · 날짜 · [+ 공고] [내 계정] [⋯ 메뉴]
       D-day 레일(내 지원 일정 + 안 담은 공고 마감, 최대 12칸)
탭     전체 공고 · 내 지원 · 캘린더 · 주간 플래너 · 아카이브 · 채용 레이더
       · (영업·세일즈) · (마케팅) · 매칭 아카이브        ( ) = 메뉴에서 켜야 보임
메뉴   내 조건 · 테마·화면 모드 · 일정 내보내기 · 공고 제보 · 업데이트 기록
       · 영업·세일즈 켜기 · 마케팅 켜기 · (계정 전용 토글) · 백업 파일 받기 · 백업에서 복원 · 로그아웃
기타   떠 있는 도움말 버튼(?)
```

탭은 숨김 포함 9개(공개 사용자 기본 7개), 메뉴는 11항목(공개 사용자 10개)이다.

**문제**

1. 공고를 보는 화면이 다섯이다(전체 공고, 채용 레이더, 영업·세일즈, 마케팅, 매칭). 출처와 관점이 다를 뿐 모두 「지원할 공고 찾기」인데, 탭이 나뉘면서 행 모양·필터·담는 버튼 이름(지원 / 지원 담기 / 버튼 없음)이 제각각이 됐다. 사용자는 찾는 공고가 어느 출처에서 왔는지 알아야 한다.
2. 날짜 화면이 둘이다. 캘린더(월)와 주간 플래너(주)는 범위와 할 일 유무만 다르다.
3. 이름이 겹친다. 아카이브, 매칭 아카이브, 코드의 보관함(마감 공고)이 같은 말을 다른 뜻으로 쓴다.
4. 탭 순서와 무게가 사용 빈도와 맞지 않는다. 경력 공고가 절반 넘는 레이더와 설정이 필요한 매칭이 핵심 흐름 탭과 같은 무게로 놓여 있고, 휴대폰에서는 처음에 화면 밖에 있다(mob-list-fold).
5. 메뉴에 성격이 다른 일이 한 줄로 섞여 있다. 필터(내 조건), 설정(테마), 기능 켜기(모아보기), 데이터(백업·복원), 계정(로그아웃)이 같은 모양이고, 기능을 켜면 탭이 생기는 동작은 예측하기 어렵다.
6. 헤더 자리 배분이 거꾸로다. 가끔 쓰는 「내 계정」이 버튼 하나를 차지하고, 매일 보는 목록을 바꾸는 「내 조건」은 메뉴 안에 있다.

**그 밖의 문제**

- 광고 카피·과장 형용사·명언체는 화면 문자열에서 찾지 못했다. 고칠 대상은 홍보 문체보다 말투 혼재와 내부 용어다.

- 왜: 새로고침, 뒤로 가기, 링크 공유가 예상대로 동작해야 한다(G-10, J-04).

### B-2 「오늘」 대시보드 (A/B 테스트 B안)

**목적**: 앱을 열면 지금 할 일이 먼저 보이게 한다. 핵심 흐름 중 마감 확인과 결과 기록을 첫 화면으로 당긴다. 결과 기록은 실사용에서 가장 밀리는 일이라 다른 화면으로 가지 않고 한 번 눌러 끝내게 한다.

**위치**: B안의 첫 탭이자 로그인 직후 시작 화면(`#/today`). B안에서는 헤더 레일을 숨긴다.

**머리**: 「10월 14일 수요일」(날짜 숫자 세리프) + 요약 한 줄. 0이 아닌 항목만 「마감 2건 · 결과 확인 3건 · 이번 주 전형 1건」처럼 잇고, 모두 0이면 「오늘 챙길 일정이 없어요.」

**블록과 우선순위**

| 우선 | 블록 | 보여 줄 것(판정) | 행에서 하는 일 | 최대 행 | 빈 상태 문구 |
|---|---|---|---|---|---|
| 1 | 내 마감 | 담은 공고 중 서류 결과가 「대기」이고 서류 마감이 오늘~14일 안인 것, 날짜가 있는 전형 일정(오늘~14일). D-day 순. 예상 날짜에는 「예상」 꼬리표(B-3-3) | 행 누르기 → 공고 상세. 마감 시각을 모르면 행 안 「시각 넣기」(시각 입력 인라인). 「원문 ↗」 | 5 + 「모두 보기」(내 지원) | 「앞으로 14일 안에 마감하는 공고가 없어요. 공고 탭에서 담으면 여기에 D-day가 떠요.」 [공고 보기] |
| 2 | 결과 확인 필요 | B-3-1의 「확인 필요」(발표 예정일이 지났거나, 없으면 서류 마감 후 14일이 지났는데 결과가 대기) + 손으로 표시한 것. 오래된 순 | [서류 합격] [탈락] [아직 몰라요]. 전형이 진행 중이면 [{단계} 합격] [탈락] [아직 몰라요]. 「아직 몰라요」 → 7일 동안 이 블록에서 숨김(`snooze`) | 5 + 「n건 더 보기」 | 「지금 결과를 적을 공고가 없어요.」 |

순서의 이유: 마감은 놓치면 되돌릴 수 없어서 맨 위. 결과 기록은 급하지 않지만 쌓이면 지원 현황 전체가 틀어지고 실사용에서 가장 밀리는 일이라 둘째. 전형은 준비가 필요한 일정이라 셋째. 할 일은 개인 메모, 새 공고 탐색은 시간이 날 때 하는 일이라 아래.

- 내 지원 화면(표·카드)에서는 공고 상태 알약(접수 중 등)을 쓰지 않는다(M-07).
- 실험 2 B: 「제출 전」이 「마감 전」 자리를 대신한다(확인 필요 > 탈락 > 합격·진행 > 제출 전 > 결과 대기 > 미지원). [제출했어요]를 누른 공고는 마감 전이어도 「결과 대기」로 보이고, 표 타일도 「마감 전」 자리에 「제출 전」이 들어간다. 서류 결과를 합격·탈락으로 바꾸면 제출한 것으로 본다(`sent: true`). 「제출 전」은 확인 필요 자동 판정에서 뺀다(03 문서 3.3).
- 전형 단계로 넓히기(다음 릴리스 제안, 02 문서 B02 범위 밖): 날짜가 지난 전형의 결과가 7일 넘게 「준비」나 「결과 대기」면 확인 필요로 본다. 7일은 임시값이다.

**B-3-2 전형 단계 칩과 트랙**

- 문구 형식은 「{단계 이름} {결과}」이고 결과 단어는 준비 · 결과 대기 · 합격 · 탈락 네 가지만 쓴다.
- 단계 이름 표기: 서류, 서류 발표, AI 역량검사, 적성검사, 인적성검사, GSAT, 필기전형, 과제, 1차 면접, 2차 면접, 최종 면접. 화면 문자열의 「서류합격」「최종합격」은 「서류 합격」「최종 합격」으로 띄어 쓴다(내부 비교 키 `stKey`는 그대로).
- 「불합격」은 화면에 쓰지 않고 「탈락」으로 쓴다. 데이터 값 `불합격`은 유지한다.
- 서류 결과 선택 목록: 「서류 결과 대기 / 서류 합격 / 서류 탈락」.
- 전형 결과 선택 목록(`.st-res`): 「준비 / 결과 대기 / 합격 / 탈락」(데이터 예정 / 완료 / 합격 / 불합격에 대응).

**B-3-3 D-day 규칙(레일·오늘·내 지원·캘린더·공고 알약 공통)**

| 마감·일정까지 | 문구 | 글자색 | 칩 배경 |
|---|---|---|---|
| 지남 | 「n일 지남」 | `--muted` | 없음 |
| 0일 | 마감이면 「오늘 마감」, 전형이면 「오늘」 | `--urgent`, 굵게 | `--urgent-soft` |
| 1~3일 | 「D-1」~「D-3」 | `--urgent` | `--urgent-soft` |
| 4~10일 | 「D-4」~「D-10」 | `--amber` | `--amber-soft` |
| 11일 이상 | 「D-11」… | `--ink-2` | `--paper` |

예상 날짜(02 문서 B05): 칩 테두리를 점선으로 바꾸고 D-day 뒤에 「예상」을 붙인다(「D-3 · 예상」). 0일이면 한 줄로 쓰는 곳은 「예상 마감 오늘 · 공고 확인」, 레일 칩처럼 큰 글자와 설명이 나뉘는 곳은 큰 글자 「오늘」과 설명 「예상 마감 · 공고 확인」으로 쓴다. 색은 위 표를 따르고, 레일 칩은 왼쪽 색 띠를 유지한 채 나머지 테두리만 점선으로 바꾼다.

숫자는 세리프로 쓴다. 레일 칩의 기존 `.u`/`.s` 클래스 규칙을 그대로 따른다.

### B-4 prompt()/confirm() 대체

원칙:
- 글을 받는 곳은 **인라인 입력**.
- 되돌릴 수 있는 일(기록이 그대로 있는 「빼기」, 빈 항목 지우기, 이전 내용을 메모리에 둘 수 있는 덮어쓰기)은 **바로 실행하고 되돌리기 토스트**.
- 되돌릴 수 없는 일과 여러 건을 한꺼번에 바꾸는 일은 **확인 창**.

**B-4-a 인라인 입력 `.inl`**

```html
<!-- 「+ 할 일」을 누르면 버튼 자리에 나타난다 -->
<form class="inl" data-kind="todo" data-date="2026-10-14">
  <label class="sr-only" for="inl-todo-20261014">수요일 할 일</label>
  <input id="inl-todo-20261014" type="text" maxlength="80"
         placeholder="할 일 적기" autocomplete="off" enterkeyhint="done">
  <button type="submit" class="primary sm" disabled>추가</button>
  <button type="button" class="ghost sm" data-act="close">닫기</button>
</form>
```

```css
.inl{display:flex;gap:6px;align-items:center;width:100%}
.inl input{flex:1;min-width:0;min-height:36px}
.sr-only{position:absolute;width:1px;height:1px;margin:-1px;padding:0;overflow:hidden;
  clip:rect(0,0,0,0);white-space:nowrap;border:0}
@media (max-width:640px){ .inl input,.inl button{min-height:44px} }
```

- 트리거를 누르면 그 자리에 폼이 나타나고 입력칸에 포커스가 간다.
- Enter는 제출, Esc는 닫기(입력 버림). 빈 값이면 [추가]가 비활성이다.
- 연달아 넣는 곳(할 일, 전형 추가)은 제출 뒤 칸을 비우고, 입력칸이 열린 채로 다음 입력을 받는다. 한 번만 넣는 곳(직무, 전형 순서)은 제출하면 닫힌다.
- 닫히면 포커스는 트리거 버튼으로 돌아간다. 바깥을 눌렀을 때 입력값이 있으면 그대로 두고, 비었으면 닫는다.

**B-4-b 되돌리기 토스트**

```html
<div class="toast" id="toast" role="status" aria-live="polite">
  <span class="toast-msg">B사 · 내 지원에서 뺐어요</span>
  <button type="button" class="toast-act">되돌리기</button>
</div>
```

- 동작 버튼이 있으면 6초, 없으면 글자 수에 따라 3~7초(기본 3초에 20자마다 1초). 마우스가 올라가 있거나 포커스가 있으면 시간을 멈춘다.
- 「되돌리기」는 실행 직전 상태로 돌리고 「되돌렸어요」를 띄운다.
- 새 토스트가 뜨면 앞 토스트의 되돌리기는 확정된다.
- 휴대폰은 화면 아래 좌우 14px 여백, 버튼 높이 44px.

**B-4-c 확인 창 `ask()`**

```html
<dialog id="askDlg" class="ask" aria-labelledby="askTitle" aria-describedby="askBody">
  <h2 id="askTitle">직접 추가한 ‘B사’ 공고를 지울까요?</h2>
  <p id="askBody" class="sub">이 공고에 적은 자소서·전형 기록도 함께 지워지고 되돌릴 수 없어요.</p>
  <div class="f-actions">
    <button type="button" class="ghost" data-v="close">닫기</button>
    <button type="button" class="ghost" data-v="extra" hidden></button>
    <button type="button" class="primary is-danger" data-v="ok">공고 지우기</button>
  </div>
</dialog>
```

- 호출: `ask({title, body, ok, tone:"danger"|"normal", extra})` → `Promise<"ok"|"extra"|"close">`. 창 하나를 재사용한다.
- 위험한 작업은 첫 포커스를 「닫기」에, 보통 작업은 주 버튼에 둔다. Esc와 바깥 누르기는 「닫기」와 같다. 닫히면 포커스는 창을 연 버튼으로 돌아간다.
- 위험 버튼: `.primary.is-danger{background:var(--urgent);color:var(--on-accent)}` — 밝게 5.69:1, 어둡게 7.60:1.
- 문구: 제목은 질문형(「~할까요?」), 본문은 사라지는 것을 구체적으로(건수·글자 수), 버튼은 동작 이름. 「확인」「예」「취소」는 쓰지 않는다.
- 휴대폰: 버튼 2개는 한 줄, 3개면 세로로 쌓고 주 버튼을 맨 아래에 둔다. 높이 44px.

### B-5 저장 상태 표시

| 상태 | 언제 | 데스크톱 표시 | 휴대폰 표시 | 색 |
|---|---|---|---|---|
| 저장됨 | 마지막 저장이 성공했고 보낼 변경이 없음 | 「✓ 저장됨」, `title`에 「10:42에 저장」 | 「✓」만 | `--muted` |
| 저장 중 | 서버 요청이 400ms 넘게 걸림 | 「저장 중…」, 앞의 점이 천천히 깜박임(움직임 줄이기 설정이면 멈춤) | 점만 | `--muted` |
| 오프라인 | `navigator.onLine`이 false이거나 네트워크 오류 | 「오프라인 · 이 기기에만 있어요」 | 「오프라인」 | `--amber` |
| 저장 못 함 | 서버가 오류로 답함(권한·용량 등) | 「저장 못 했어요」 + [다시 시도] | 「저장 못 함」 + [다시 시도] | `--urgent` |
| 다른 기기와 겹침 | 불러온 뒤 다른 기기에서 더 나중에 저장된 것을 발견 | 헤더 아래 안내 띠 | 같은 띠 | `--st-check-*` |

동작:
1. `save()`가 불리면 표시를 바꾸지 않고 변경 대기로 본다. 800ms 디바운스 뒤 요청을 보내고, 400ms가 넘으면 「저장 중…」, 성공하면 「저장됨」과 시각을 기록한다(짧은 저장마다 표시가 깜박이지 않게).
2. 오프라인이면 이 기기 캐시에는 계속 저장한다. `online` 이벤트가 오면 자동으로 다시 보내고, 성공하면 토스트 「다시 연결돼서 저장했어요」.
3. 저장 못 함은 한 번 자동으로 다시 보내고, 그래도 실패하면 [다시 시도]로만 보낸다(02 문서 B08). 오류 원문은 콘솔에만 찍는다.
4. 겹침: 불러올 때 받은 `updated_at`을 기억하고 저장 직전에 서버 값과 비교한다(비교 방법은 개발 결정). 다르면 자동 저장을 멈추고 띠를 띄운다. 탭이 다시 보일 때(`visibilitychange`)도 확인해 일찍 알린다.
5. 변경 대기·저장 중·오프라인·저장 못 함 상태에서 페이지를 떠나려 하면 `beforeunload` 경고를 띄운다.

**B-6-1 마감 구간 묶음과 「더 보기」(공고 목록)**

### B-8 문구 가이드

**B-8-1 말투: 해요체 하나로**
- 평서문 「~해요 / ~예요 / ~었어요」, 부탁 「~해 주세요」, 질문 「~할까요?」. 방법을 알려 줄 때는 「~하면 돼요」.
- 이유
  1. 10월에 더한 기능(레이더·매칭·현황표·로그인·각주·업데이트 기록)이 이미 해요체라 앞으로 늘어날 문구와 방향이 같다.
  2. 토스트·빈 상태·버튼 옆 안내처럼 짧은 문장이 많다. 「없어요」「담았어요」가 「없습니다」「담았습니다」보다 짧아 휴대폰 한 줄에 더 들어간다.
  3. 부탁 문장 「~해 주세요」가 이미 해요체 계열이라 「~합니다. ~하세요」처럼 한 화면 안에서 말투가 바뀌는 일이 없어진다.
  4. 국내 소비자 서비스의 UI 문구 관례(당근 Seed 글쓰기 기준 등)가 해요체이고, 주 사용자가 매일 쓰는 앱들의 말투와 맞는다.
- 고칠 양은 합쇼체 평서문 약 94문장이다. 대부분 도움말, 내 지원·아카이브 설명, 토스트, 오류 문구에 있다. B-8-6 교체표부터 바꾼다.
- 경고와 오류도 해요체로 쓴다. 무게는 말투 대신 내용(무엇이 사라지는지)과 버튼 색으로 준다.

**B-8-2 표기**
- 띄어쓰기: 「해 주세요」「넣어 주세요」처럼 띄어 쓴다(지금 붙여 쓴 곳 4곳). 「서류 합격」「최종 합격」「확인 필요」.
- 숫자는 아라비아 숫자. 날짜는 문장에서 「10월 14일 (수)」, 좁은 곳에서 「10/14」. 시각 「15:00」, D-day 「D-3」, 지난 날 「3일 지남」, 당일 「오늘」.
- 단위: 공고·지원·일정은 「건」, 키워드·파일·카드처럼 물건은 「개」.
- 마침표: 문장으로 된 안내와 토스트에는 찍고, 버튼·제목·칩·라벨·입력칸 안내에는 찍지 않는다.
- 기호: 줄표(—)로 두 내용을 잇지 않고 두 문장으로 나눈다. 가운뎃점(·)은 나열과 묶음 구분에만 쓴다. 「⚠」는 쓰지 않는다.

**B-8-3 버튼 동사 규칙**
1. 버튼 이름은 동작 하나를 명사형으로 쓴다: 담기, 빼기, 저장, 지우기, 바꾸기, 되돌리기, 불러오기, 내보내기, 닫기. 대상을 밝혀야 하면 「대상 + 동작」(「공고 지우기」「백업 파일 받기」).
2. 「~하기」를 붙여 늘이지 않는다(「지원하기」 → 「담기」). 다른 화면으로 가는 버튼은 「{화면} 보기」(「내 지원 보기」).
3. 창을 닫는 버튼은 「닫기」 하나로 쓴다. 「취소」는 쓰지 않는다(「지원 취소」와 헷갈리고 무엇을 취소하는지 알 수 없다).
4. 위험한 동작은 무엇이 사라지는지 이름에 넣는다(「공고 지우기」「모두 지우기」). 「확인」「예」「OK」는 쓰지 않는다.
5. 켜고 끄는 버튼은 이름에 상태를 넣지 않는다. 세그먼트·체크박스·`aria-pressed`로 상태를 보인다.
6. 주 버튼은 창마다 하나, 오른쪽 끝(휴대폰은 맨 아래)에 둔다. 위험한 주 버튼은 `is-danger`.
7. 같은 동작은 어느 화면에서나 같은 이름을 쓴다(B-8-5).

공통 규칙:
- 휴대폰 터치 대상은 44×44. 보이는 크기가 작으면 패딩이나 `::after`로 누르는 영역을 넓힌다.
- 입력 글자는 16px(iOS 확대 방지, 지금 규칙 유지).
- 그리드·플렉스 자식은 `min-width:0`. 긴 회사 이름은 한 줄 말줄임 또는 `overflow-wrap:anywhere`.
- 고정 요소는 `env(safe-area-inset-*)`를 반영한다(지금 도움말·토스트 규칙 유지).
- 휴대폰에서 떠 있는 버튼으로 내용을 가리지 않는다(G-12).
